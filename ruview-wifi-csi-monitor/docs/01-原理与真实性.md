# 01 原理、项目识别与真实性

## 找到的高星项目

- 仓库：<https://github.com/ruvnet/RuView>
- 项目名：π RuView
- 旧称/关键词：WiFi DensePose、Wi‑Fi CSI sensing
- 许可证：MIT
- 官方 ESP32 固件目录：`firmware/esp32-csi-node`

## 它为什么不是超声波

超声波使用几十 kHz 的机械声波，需要超声波发射器和接收器。RuView 使用 2.4/5 GHz 电磁波，也就是 Wi‑Fi 无线电信号。

Wi‑Fi OFDM 把一个频道分成很多子载波。CSI 描述每个子载波的幅度和相位。人在路由器和接收节点附近移动时，反射、多径和遮挡发生变化，CSI 随之变化。

```text
路由器发出Wi‑Fi包
       ↓
直达路径 + 墙面反射 + 家具反射 + 人体反射
       ↓
ESP32-S3收到包并读取各子载波CSI
       ↓
滤波、相位/幅度特征、时间窗口
       ↓
存在/运动启发式或机器学习模型
```

## 为什么普通路由器不够

普通路由器确实已经产生 Wi‑Fi 信号，但普通固件不会把底层 CSI 提供给应用程序。普通 Windows 网卡通常只暴露 RSSI，即一个粗略的信号强度值。

RuView 需要类似下面的数据：

```text
第1个子载波：幅度 + 相位
第2个子载波：幅度 + 相位
……
第56/64个子载波：幅度 + 相位
连续数百个时间帧
```

ESP32-S3 的 Wi‑Fi 驱动可以提供 CSI 回调，所以它在家庭方案中充当 CSI 接收器。家庭路由器仍然是正常 AP，不需要刷机。

## 如何分辨模拟数据与真实数据

以下情况不能证明房间被真实监控：

- 只运行 `docker run` 就出现平滑人体骨架；
- 没有任何 CSI 硬件，界面却持续输出动作；
- 服务端使用 `--source simulated`；
- 使用 `--source auto`，但没有确认它没有回退；
- UI 有动画，但服务端没有 ESP32 节点、帧率和 UDP 包日志。

真实验收必须同时满足：

1. ESP32 串口显示已连接你的 Wi‑Fi；
2. ESP32 的目标 IP 是运行服务端的电脑；
3. Windows UDP 5005 能收到来自节点的数据；
4. 服务端明确使用 `--source esp32`，不允许模拟回退；
5. 日志或节点 API 显示实际节点 ID、RSSI、包率/CSI 形状；
6. 人进入和离开 RF 链路时，真实特征发生可重复变化。

## 官方披露的限制

官方 README 对当前模型状态有较坦率的说明：在线第一版姿态模型精度较弱，一些运行路径曾是 `confidence=0` 的占位输出；MM-Fi 数据集上的高指标不等于在你家零标定就有同样效果。

因此教程不以“穿墙显示精确骨架”为验收目标。新手应该先完成真实 CSI 接收和存在/移动实验。
